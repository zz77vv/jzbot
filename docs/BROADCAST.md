# 客户广播

后台首页 → 客户广播 → 新建广播 → 选择范围（可多选）→ 输入纯文本 → 预览 → 确认发送。
只接受管理员与 Bot 私聊；每个查询、确认、控制、结果页都按 owner 隔离。

范围：

- 有交易记录：有 ledger 入金/出金/清账，或已有成功管理员归零记录的账本。
- 存款：当前余额 ≥ 0，零余额包含在内。
- 欠款：当前余额 < 0。

仅有资料但无钱包/交易的客户不会因为缺省余额为零被加入。内部状态标记不改变上述
筛选，选择页明确显示包含内部标记客户。多选使用同一 owner 钱包集合的并集，无重复。
与后台原正余额列表的口径独立；本次不更改其统计和列表行为。

正文最多 2000 个 UTF-16 单位，保留原文与换行，作为纯文本发送。接收名单最多 1000 人。
预览显示完整正文、范围、去重人数和前五名客户；确认五分钟有效。确认前重新核对
接收 ID 集合，余额变化导致筛选名单变化时要求重新预览。确认后正文、名单固定。
重复确认复用同一任务；每个 owner 最多一个发送中或暂停任务，取消/完成后可新建。

发送使用现有 Bot/HTTP 生命周期，无第二个 polling。独立 worker 最多约每 1.2 秒一条，
有到期账务回执时优先处理回执。每次刷新最多八个 owner 对应连接，检查返回 ID、owner、
enabled、可读取的 can_reply；明确连接/权限失效可换下一个，网络异常不会停用账本连接。
不会为检查连接发送点号。广播本身静默，不引用原指令、不置顶、不改账、不写财务 Outbox。

Telegram 官方限制：BusinessBotRights.can_reply 针对最近 24 小时收到过来信的私聊。
选择历史客户不能绕过此限制；最终由 Telegram 按连接及聊天状态决定能否发送。
依据：https://core.telegram.org/bots/api#businessbotrights
默认免费群发限流依据：https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this
不使用付费广播参数。

结果分页显示等待、正在发送、已发送、失败、不确定、取消及保守原因。已发送只表示
API 返回成功及消息 ID，不代表客户已读。连接刷新网络错误安全重试最多三次；RetryAfter
写入持久冷却并最多三次尝试，不立即循环。发送网络超时可能已被接收，标记不确定且
不自动重发。未知明确拒绝保留失败结果；不确定结果不提供盲目重发按钮。

暂停/取消阻止后续发送，已提交给 Telegram 的在途消息无法撤回。继续只处理尚待发送
的客户。重启将进行中的任务暂停，将 sending 收件项转为不确定；不会自动群发。
发送成功后的确认落库异常会停止广播 worker，保留现场，不能继续向其他客户发送。
后台显示 worker 不可用，账务回执 worker 独立。修复并重启后先检查不确定项。

独立队列：日志目录/broadcast.db，文件权限 0600；包含管理员正文和客户投递状态，属于
生产运行数据，和 WAL/SHM 一起严格保护。不上传 GitHub，不从本地部署，不自动备份或删除。
不改变原 ledger.db 的表、索引、迁移版本或账务数据。

本地修改、完整测试、脱敏审计与 GitHub 发布之后才部署；上传必要代码，服务器完整
测试通过后精确重启，追加日志，核验新 worker、单实例锁、原账本及其他机器人。
测试全部使用临时数据库和 Mock；上线验收不向真实客户发送广播测试。
